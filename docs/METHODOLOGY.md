# Methodology

## Research question

When an AI assistant rewrites an application, does a security proof that **re-discovers the moved endpoint** catch an authorization regression that a **route-pinned saved test** misses — without ever reporting a vulnerable application as safe?

## Hypothesis (pre-registered)

Committed in `eval/benchmark/HYPOTHESIS.md` (commit `01b0ee0`) **before any benchmark harness code existed**:

> Self-relocating re-discovery detects seeded authorization regressions across varied route rewrites where frozen tests and static scanners fail — and never reports `NO_LEAK_DETECTED` on a seeded-vulnerable app.

## Study 1 — default security of AI-generated apps

- **Setup:** 23 applications generated by one model from ordinary prompts that contain no security terms.
- **Finding:** 6 of 23 shipped a forgeable session secret; 17 did not. 0 of 23 reproduced a cross-user leak.
- **Interpretation:** AI-generated security is *inconsistent* — the same kind of prompt yields secure and insecure apps, indistinguishable from the outside.

## Study 2 — rewrite-survival benchmark

**Design.** 25 **synthetic route transformations** of one base application, generated programmatically:

| Type | Transformation | Count |
|---|---|---:|
| A | In-dictionary resource + known API prefix | 8 |
| B | Unfamiliar resource name | 5 |
| C | Nested route | 4 |
| D | Alternate request/response structure | 4 |
| Control | Ownership check intact | 4 |

Each of the 21 vulnerable cases carries a labeled, seeded ownership-check removal.

**Detectors compared:** Sudarshan's self-relocating verification; a frozen route-pinned saved test; static analysis (gitleaks, and a generic local semgrep rule — the community ruleset was unreachable offline).

**Metrics:** detected / inconclusive / falsely cleared, with two-sided 95% Wilson score intervals. The full run was reproduced twice with identical results.

## Results

| Outcome (21 seeded-vulnerable apps) | Result | 95% Wilson CI |
|---|---:|---|
| Detected | 8 / 21 | [0.21, 0.59] |
| Inconclusive | 13 / 21 | [0.41, 0.79] |
| **Falsely cleared** | **0 / 21** | **[0.00, 0.155]** |
| Secure controls correctly cleared | 4 / 4 | [0.51, 1.00] |

By type: A — 8/8 detected (CI [0.68, 1.00]); B, C, D — all inconclusive. Frozen saved tests detected 0/21. Static baselines produced no discriminating verdict.

## Threats to validity

- **Internal:** expected outcomes were assigned per transformation type, so the benchmark is a controlled *compatibility* test, not a blind generalization experiment.
- **External:** all 25 cases derive from one base application; they are not independent real-world applications.
- **Construct:** gitleaks is a secrets scanner and the semgrep rule is generic; neither is a purpose-built authorization tester. Baselines represent what a developer typically reaches for, not the strongest available competitor.
- **Statistical:** with N = 21 and N = 4, intervals are wide; we report them rather than point estimates alone.

## Next experiments

1. A **blind holdout**: freeze the implementation, then evaluate on applications the team has never seen.
2. A purpose-built authorization baseline (e.g. a spec-driven multi-user test harness), compared on detection, inconclusive rate, false alarms, and setup effort.
3. Semantic endpoint discovery, measured on the B/C/D categories that are currently inconclusive.

## Reproducing

```bash
npm ci
npm test        # typecheck + the three demo verdicts
npm run bench   # the 25-case benchmark → eval/results/rewrite-benchmark.json
```
